# NeptHass v1.0.0-rc.1 release-candidate draft

Status: **draft only; not tagged or published**.

## Draft release notes

NeptHass v1.0.0-rc.1 is the proposed first release candidate for the stable self-hosted Discord-first bridge for Home Assistant. It consolidates the functionality released through v0.5.0 plus the unreleased sensor-registry hardening. It introduces no new network listener, configuration variable or database migration.

Highlights:

- Interactive `/setup`, entity discovery, aliases and `/sync`.
- Deny-by-default read/control permissions, with control restricted to lights and switches.
- Home Assistant REST and WebSocket integration with reconnection and reconciliation.
- Conservative sensor monitoring and `/health` reporting.
- Notification rules with duration, hysteresis, unit-bound thresholds and bounded start-up behavior.
- Audit logging, replay protection, rate limiting and secret redaction.
- Neutral sensor presentation: raw `on` is never automatically shown as healthy.
- Static non-root distroless container build and transactional SQLite migrations.

This candidate must not be used as a life-safety alarm. Notifications are best-effort and can be delayed, duplicated or lost during a crash or restart.

## Compatibility and migrations

- Configuration is compatible with v0.5.0; no variable is added or removed.
- The candidate adds no migration. The latest schema remains migration `0004`.
- A v0.5.0 database opens without a schema change.
- Databases from v0.1.0 through v0.4.0 migrate forward in order.
- Older binaries refuse a database whose migration set is newer than they understand.
- Internal Go packages are not a supported public library API.
- The documented production path remains Linux with Docker Engine and Compose; other host/architecture combinations are not all release-tested.

## Upgrade from v0.5.0

1. Record the currently running version and keep the old source/image available for rollback.
2. Stop only the NeptHass container. Do not remove the named data volume.
3. Back up the complete `/data` volume and `.env`/secret-file configuration.
4. Build the candidate from the exact reviewed commit; record its commit ID and image digest.
5. Start the candidate and inspect redacted startup logs.
6. Verify `/health`, `/devices`, `/sensors`, `/notifications status` and `/notifications list`.
7. Exercise one authorized status request and one light/switch control in the test environment.
8. Retain the backup until the release is accepted.

## Rollback plan

Because rc.1 adds no migration, rollback to v0.5.0 should use the pre-upgrade database backup and the previous image/source revision:

1. Stop only the NeptHass candidate container.
2. Preserve the failed candidate database separately for diagnosis.
3. Restore the full pre-upgrade `/data` backup; do not mix individual SQLite/WAL files from different snapshots.
4. Restore the previous configuration and start the known-good v0.5.0 image/source revision.
5. Verify `/health`, permissions, aliases and notification settings.

If a future candidate adds a migration, never point an older binary at the upgraded database; restore the matching backup instead.

## Known limitations

- One Discord guild and one NeptHass process are supported.
- Notifications are in-memory and best-effort, not a guaranteed emergency channel.
- Pending notifications may be lost on crash/restart and may occasionally duplicate.
- Events that occur and reverse entirely during a Home Assistant outage cannot be reconstructed.
- Dynamic sensor configuration and smoke/gas/carbon-monoxide behavior are outside this release.
- No official container registry, image-signing method or binary artifact channel is approved yet.
- Native Windows/macOS execution and every container architecture have not been release-tested.

## Security, distribution and provenance decisions

Release blockers:

- Enable and verify a private vulnerability-reporting channel. Do not publish an invented email address.
- Decide whether distribution is source-only or includes a container registry.
- If publishing an image, choose the registry, immutable tag/digest policy, SBOM format, provenance attestation and signing identity/tool.
- Build release artifacts only from the reviewed tag in CI, not from a maintainer workstation.
- Record the source commit, dependency lock files, builder/base image digests, artifact checksums and signatures in the release.
- Complete or explicitly waive an independent security review.

The current Dockerfile already produces a static non-root distroless image, but that build property does not by itself establish artifact provenance or publisher identity.
