## 3. Architecture review

```
Home Assistant -> WebSocket Monitor -> Sensor Registry -> Notification Engine -> Queue -> Discord delivery -> SQLite state/audit
```

1. **Monitor.** `monitor.Monitor.Run` (monitor.go:167) keeps one WebSocket session, takes a snapshot, then `process` (:268) parses each `state_changed` event and applies it to the `Tracker` under its lock; the resulting `Change` is handed to the engine synchronously and in order by `emit` (:289), with panics contained.
2. **Sensor registry.** One typed table (registry.go) defines every supported class: domain, device class, labels, binary polarity and meanings, numeric range and documented units, default cooldown, the explicit hazard flag and the rule capabilities. `Classify` (classify.go:28) reads it; an unknown class is not monitored and cannot be used in a rule. Smoke, gas and carbon monoxide are deliberately absent.
3. **Engine intake.** `Engine.OnChange` (engine.go:211) is O(1) and never touches the database; it records the change in a bounded mailbox (mailbox.go:109), keeping an ordered trail only for sensors with a stateful rule.
4. **Evaluator.** One goroutine (`evaluate`, engine.go:290): drain the mailbox, reconcile new rules (:329), evaluate each entity (:512, `observe` :579), fire due durations (:619), flush the start-up summary (initialstate.go:146), emit a bounded digest. One timer serves every pending duration.
5. **Queue and dispatcher.** Two lanes (the critical lane is never evicted by a lesser message); the dispatcher (dispatcher.go:78) re-checks sharing immediately before each send (:250), retries with backoff until a 10 minute TTL, and has a circuit breaker.
6. **Delivery and durable state.** The Discord notifier sends over REST with empty `allowed_mentions`. Only after a confirmed delivery does `Engine.delivered` (engine.go:885) write a hazard mark or the summary time to SQLite.
7. **Audit.** Configuration changes are audited atomically by the service; refused administrator commands are recorded by `audit.Denials` (denials.go:92) with fixed reasons, rate limits and a retention cap.

**Where each concern is enforced**

| Concern | Where |
| --- | --- |
| Authorization | Every interaction type is authorized first (`Bot.handleInteraction`, interaction.go:58); administrator level is enforced at the command gate (`Registry.Run`, registry.go:~175) **and** again in every service method; autocomplete is administrator-only. Sharing is re-checked at evaluation (engine.go:446), when a duration comes due (:619), before the summary is sent, and at dispatch (dispatcher.go:250). |
| Unit validation | Creation: `Service.AddRule` (service.go:212) accepts only a unit documented for the class and binds it. Evaluation: `unitOK`/`usable` (rules.go:86, :114): a reading in another unit is never compared and nothing is converted. Legacy rules: `ConfirmUnit` (service.go:346), `BindLegacyUnits` (:397), engine trigger (engine.go:483, :872). |
| Duration evaluation | `observe` starts an episode on NeptHass's own clock (engine.go:579); `fireDue` re-reads the sensor and sharing when it is due and fires nothing while monitoring is unhealthy (:619); `reseedEpisodes` restarts counts after an outage (:672). Home Assistant's `last_changed` is never used for timing. |
| Hysteresis | `cleared` (rules.go:155) and the rule's armed state (engine.go:579); a rule found already above its threshold at start begins disarmed (initialstate.go:56). |
| Restart recovery | Episodes and armed state are in memory only. At start `reconcileStates` (engine.go:329) seeds rules from the tracker: a hazard becomes one initial alert, other conditions one summary, a duration counts from the first sighting ("at least"). Only the delivery marks (`notification_marks`) and the last summary time survive a restart, written after confirmed delivery. |

## 8. Database migration findings

- **Correctness.** `0004` rebuilds `notification_rules` in one transaction: every rule keeps its ID, the AUTOINCREMENT sequence is preserved (a rule ID is never reused in the audit trail), thresholds, cooldown and authorship carry over, existing rules become immediate rules with no clear value and no unit, and the 200-rule trigger is recreated. It adds `notification_marks` (foreign key to the rules, cascade delete) and `notification_settings.startup_summary_at`.
- **Evidence.** Six dedicated tests, run 3 times each with the race detector in gate U07 and once more in U05/F04: upgrade of a v0.4.0 database with adversarial data, constraints and the rule limit, marks following their rule, an injected failure halfway (everything rolls back, the original is untouched), a fresh database, and concurrent writers. They use the production connection settings.
- **Compatibility.** A v0.4.0 binary refuses a database that has migration 0004 (`Migrate_refusesDatabaseFromNewerBuild`); going back requires restoring a backup, which the upgrade notes state. The maintainer's own v0.4.0 database upgraded with its legacy rule #4 intact (user-reported).
- **No finding.** Idempotency, checksums and the contiguous-sequence rule of the runner are unchanged and tested.

## 9. Known limitations and accepted risks

- After a crash between Discord accepting a message and the mark write, a hazard alert or summary repeats once (a duplicate, never a loss). Tested and documented.
- Duration counts are in memory: after a restart or a monitoring outage they restart (late, never early; "at least").
- The narrow seeding window of S2.
- No persisted outbox; a 10 minute staleness bound; one alert channel; possible duplicates (as in v0.4.0).
- Smoke, gas and carbon monoxide are not supported (deliberate).
- Real Discord rate limits and Discord-only outages are not exercised by any automated test.
